## Вызовы методов API (`src/vk/api.js`)

- Все вызовы идут через `vkApi(method, params)` в `src/vk/api.js` — единственное место, где
  заданы домен, версия и способ передачи ключа.
- **Домен — `api.vk.ru`.** Документация требует именно его; `api.vk.com` на 2026-09-26 ещё
  отвечает, но в документации больше не упоминается. До 2026-09-26 бот ходил на `api.vk.com`.
- **Ключ — в заголовке `Authorization: Bearer <ключ>`**, как требует документация. Раньше ключ
  шёл параметром `access_token` в URL (такие URL оседают в логах прокси и HTTP-клиентов).
- **Версия — `v=5.199`**: последняя в списке версий, на ней же опубликована официальная
  JSON-схема. Страница «Формат запросов» называет актуальной 5.131 — это устаревший текст.
  Изменения, которые нас касаются: с 5.139 `groups.getById` возвращает `{ groups: [...] }`
  вместо массива (учтено в `getVkUserName`).
- Ошибки VK приходят **в теле ответа с HTTP 200** (`{"error": {"error_code", "error_msg"}}`),
  axios их не бросает — `vkApi` возвращает `{ error }`, вызывающий код логирует.
- Лимит частоты: ошибка `6` «Too many requests per second», точные лимиты VK не публикует.
  Имена пользователей кэшируются на час (`src/utils.js`), чтобы всплеск событий не упирался в лимит.

Коды ошибок, которые встречались или вероятны у нас:

| Код | Значение | Что делать |
|---|---|---|
| 5 | Авторизация не удалась (ключ отозван/просрочен) | Выпустить новый ключ |
| 6 | Слишком много запросов в секунду | Само пройдёт; имена кэшируются |
| 15 | Доступ запрещён (в т.ч. «token required» без ключа) | Проверить ключ и приватность объекта |
| 27 | Метод недоступен с ключом сообщества | В `VK_SERVICE_KEY` ключ сообщества — заменить (см. ниже) |
| 28 | Ключ доступа приложения недействителен | Обновить сервисный ключ в настройках приложения |
| 30 | Профиль приватный | Имя не будет получено — ожидаемо |

## Ключи доступа

| Переменная | Что это | Для чего используется в коде |
|---|---|---|
| `VK_SECRET_KEY` | Произвольная строка, которую вы сами придумываете и вписываете в поле «Секретный ключ» настроек Callback API. VK присылает её в каждом запросе в поле `secret`. Это **не** ключ доступа к API | Проверка подлинности запроса на `/webhook` (`server.js`, timing-safe сравнение) |
| `VK_SERVICE_KEY` | Ключ для вызова методов API — **сервисный ключ приложения** (рекомендуется) или пользовательский токен, **не** ключ сообщества (см. ниже) | `likes.getList` (счётчик лайков), `users.get` / `groups.getById` (имена), `wall.get` + `likes.getList` (проверка при старте) |
| `VK_GROUP_ID` | Числовой ID сообщества без минуса | Ссылки на сообщество; события с другим `group_id` бот пропускает (`server.js`) |
| `VK_CONFIRMATION_CODE` | Строка подтверждения со страницы Callback API | Ответ на запрос `confirmation` |

### ⚠️ Какой ключ класть в `VK_SERVICE_KEY`

Три типа ключей VK (dev.vk.com, «Ключи доступа → Общие сведения»):

| Тип | Срок действия | `likes.getList` | `users.get`, `groups.getById`, `wall.get` |
|---|---|---|---|
| **Сервисный ключ приложения** | не ограничен | ✅ | ✅ |
| Пользовательский токен | 1 час (новые, через VK ID); старые бессрочные продолжают работать | ✅ | ✅ |
| Ключ доступа сообщества | не ограничен | ❌ **ошибка 27** | ✅ |

**Рекомендуется сервисный ключ приложения:** он бессрочный, не привязан к аккаунту человека
и подходит для `likes.getList` («Для вызова метода можно использовать: ключ доступа
пользователя, сервисный ключ доступа»). Ключ сообщества не подходит: у VK есть отдельный
allow-list разделов методов для ключей сообщества, раздела `likes` в нём нет, поэтому
`likes.getList` всегда отвечает ошибкой 27 при любых отмеченных правах. На этом проекте это
подтверждено 2026-09-14: счётчики лайков молча пропадали, хотя `users.get` работал.

Сервисный ключ пока **не проверен на этом проекте**: сейчас в Render стоит старый бессрочный
пользовательский токен, и он работает. Если будете менять — после деплоя посмотрите стартовое
сообщение (см. «Проверка при старте»).

**Как получить сервисный ключ.** Источник:
[VK ID, «Создание и настройка приложения»](https://id.vk.ru/about/business/go/docs/ru/vkid/latest/vk-id/connection/create-application),
прочитано 2026-09-26.
1. Войти в кабинет сервиса авторизации VK ID ([id.vk.com/about/business/go](https://id.vk.com/about/business/go)).
   Вход — только через **VK Бизнес ID**, нужен профиль бизнеса.
2. **Мои приложения → Добавить приложение**, указать название и платформу (Web).
3. Открыть приложение → подраздел **Информация о приложении** → **Сервисный ключ доступа**
   («используется для вызова методов API ВКонтакте в back-2-back запросах»).
4. Вставить ключ в Render → Environment → `VK_SERVICE_KEY`, сохранить и сделать **Manual
   Deploy**. Одна смена переменной без деплоя не применится
   (render.com/docs/deploys: «restarting does not incorporate those changes»).

⚠️ **Профиль бизнеса нужно подтвердить.** Без подтверждения приложения блокируются: новые — через
60 дней после создания первого приложения, старые аккаунты (до 15.12.2025) — с 1 марта 2026.
Standalone-приложения с dev.vk.com перенесены в VK ID. **Это касается и текущего токена:**
бессрочный пользовательский токен выпущен каким-то Standalone-приложением, и если это приложение
заблокируют, токен перестанет работать. Признак — стартовое сообщение
`VK_SERVICE_KEY: ❌ VK API error 5/28` или пропавшие счётчики лайков.

**Пользовательский токен через `oauth.vk.com/authorize?...response_type=token` больше не выдаётся:**
Implicit Flow и Authorization Code Flow для пользовательских ключей отключены **с 25 июня 2024**
(dev.vk.com, «Устаревшие способы получения ключей»). Новые пользовательские ключи выдаются через
VK ID и живут 1 час — для сервера без обновления токена они не годятся. Уже выпущенные бессрочные
токены (`vk1.a...`, `offline`) продолжают работать, пока их не отозвали; отсюда и токен, который
перенесли с Railway. До 2026-09-26 этот файл описывал получение токена через `oauth.vk.com` — это
устарело.

### Проверка при старте

`checkVkServiceKey()` (`src/utils.js`) вызывается при запуске, результат уходит в роль `debug`:

- `✅ OK, счётчики лайков работают` — `groups.getById` прошёл, и `likes.getList` на последнем
  посте стены вернул число;
- `⚠️ ключ валиден, но счётчиков лайков не будет — VK API error 27 …` — в переменной ключ
  сообщества;
- `❌ VK API error 5/28 …` — ключ невалиден.

До 2026-09-26 проверялся только `groups.getById`, который проходит с ключом любого типа, поэтому
«✅» не гарантировал счётчики.

## Callback API

### Подтверждение сервера

При указании адреса сервера (**Управление → Дополнительно → Работа с API → Callback API**) VK
шлёт `{"type": "confirmation", "group_id": ...}` и ждёт в ответ **строку подтверждения** со
страницы настроек, а не `ok`.

- Реализовано в `server.js` через `VK_CONFIRMATION_CODE`. Если переменная не задана, бот
  отвечает `ok` и пишет предупреждение.
- «Строка подтверждения меняется время от времени» — при добавлении нового сервера или правке
  настроек старого берите актуальную из интерфейса и обновите переменную.
- К одному сообществу можно подключить до 10 серверов, у каждого свой набор событий и версия
  API. Поэтому прод (Railway) и тест (Render) могут работать с одним сообществом параллельно.
- Типы событий включаются **отдельно для каждого сервера** (вкладка «Типы событий»);
  подтверждение само ни на что не подписывает.

### Ответ, повторы и приостановка

- На каждое уведомление сервер должен ответить строкой `ok` и HTTP 200. Бот отвечает сразу после
  проверки секрета, до обработки события.
- Если ответа нет, VK повторяет событие **через 10 с, 3 мин, 10 мин, 30 мин и 1 ч** и добавляет
  заголовок `X-Retry-Counter` с числом неудачных попыток. Бот пишет его в лог Render
  (`VK запрос: ... retry=N`). На Render free повтор почти всегда значит, что инстанс спал
  (пробуждение ~1 мин) — см. `docs/RENDER.md`.
- **«Если сервер несколько раз подряд вернёт ошибку, Callback API временно перестанет отправлять
  на него уведомления.»** Поэтому бот не ограничивает частоту аутентифицированных запросов (429 от
  нашего rate limiter тоже был бы ошибкой). Ограничиваются только запросы с неверным секретом.
- Ответ `remove` удаляет сервер. Ответ `version 5.xxx` меняет версию API сервера. Бот так не
  отвечает.
- `Retry-After` с кодами 410/429/503 просит VK отложить повтор (меньше 3 часов). Бот его не
  использует.

### Формат запроса

```json
{ "type": "<тип>", "event_id": "<уникальный ID события>", "v": "5.199",
  "object": { ... }, "group_id": 123, "secret": "<VK_SECRET_KEY>" }
```

`event_id` — ключ дедупликации. Официальная схема: «Unique event id. If it passed twice or
more — you should ignore it». Повторная доставка приходит с тем же `event_id`. Как это
используется — в `src/vk/dedup.js` и в разделе про лайки ниже.

## Лайки (`like_add` / `like_remove`)

- Поля `object`: `liker_id`, `object_type`, `object_owner_id`, `object_id`, `post_id` (только
  для комментария под записью — ID записи), `thread_reply_id`. Поля `date` нет.
- Официальные значения `object_type`: `post`, `video`, `photo`, `comment`, `topic_comment`,
  `photo_comment`, `video_comment`, `market`, `market_comment`. **На практике приходит и `clip`**
  (в документации его нет).
- Счётчик «(Всего: N)» — отдельный вызов `likes.getList` с ключом из `VK_SERVICE_KEY` (см. выше).
  У `likes.getList` нет типа `clip`. Клип в VK — это видеозапись (`clip-X_Y` и `video-X_Y`
  открывают один объект), поэтому `toLikesApiType('clip')` отдаёт `video`. **Не проверено на
  реальном ключе** (добавлено 2026-09-26). Если VK ответит ошибкой, в логе Render появится
  `[likes] likes.getList(video …)`, и счётчика у клипа просто не будет, как раньше.
- **Лайк клипа, опубликованного в посте, приходит двумя событиями:** `like_add` на `clip` и
  `like_add` на пост с этим клипом (лайки у них общие, счётчик поста растёт от каждого лайка
  клипа). `isMirroredLike()` в `src/vk/dedup.js` пропускает второе событие пары «тот же лайкер +
  clip↔post в пределах 10 с». В чат уходит одно уведомление — то, что пришло первым.
- Ссылка на объект лайка: для комментария под записью есть `post_id`; для комментариев к
  фото/видео/обсуждениям/товарам VK родителя не присылает — уведомление без ссылки (раньше
  подставлялся ID комментария, и ссылка вела на несуществующее фото).
- Дедуп (`src/vk/dedup.js`):
  1. Основной ключ — `event_id` (память 10 мин + Firestore `dedup_seen` сутки): отсекает повторы
     VK, включая пришедшие после рестарта процесса.
  2. Контентный ключ (тип + объект + актёр + дата) хранится только в памяти 60 с и страхует от
     почти одновременных дублей с разными `event_id`. Раньше он был основным и жил сутки, поэтому
     повторное действие без `date` (вступил → вышел → вступил) терялось.
  3. Ключ «захватывается» синхронно, до похода в Firestore. VK шлёт повторы параллельно, и без
     этого обе копии проходили проверку (дубли 26.09.2026).
- Старый бот (прод) показывает одно уведомление на лайк клипа из-за бага: его ключ дедупа для
  лайков не содержит ни объекта, ни лайкера, поэтому он отбрасывает **все** лайки в 10-минутном
  окне после первого, включая лайки других людей.
