# Firebase / Firestore — настройка

> Источник истины по тому, как бот использует Firebase. Заменяет прежний Supabase-стек (см.
> историю коммитов, если нужен старый SQL-based подход) — переход сделан ради бесплатного тарифа
> Firebase (Spark plan), который для тестового контура достаточен с большим запасом.

## Что нужно создать

1. [console.firebase.google.com](https://console.firebase.google.com) → **Add project** (можно без
   Google Analytics — он тут не нужен).
2. В новом проекте: **Build → Firestore Database → Create database**.
   - Режим — **Native mode** (не Datastore mode — Datastore mode не поддерживает клиентские SDK,
     которые тут не используются, но Native — стандартный выбор и для Admin SDK).
   - Локацию можно оставить по умолчанию (`nam5`/`eur3` и т.д.) — на бесплатный тариф не влияет.
   - Начните с **production rules** (правила безопасности неважны — доступ у бота через Admin SDK
     с сервисным ключом, который правила безопасности не проверяют).
3. **Project settings (⚙️) → Service accounts → Generate new private key** — скачается JSON-файл
   вида `<project>-firebase-adminsdk-xxxxx.json`.
4. Откройте файл текстовым редактором, скопируйте **всё содержимое целиком** (это валидный JSON,
   одна строка ничего не требует экранировать вручную) → вставьте как значение переменной
   окружения `FIREBASE_SERVICE_ACCOUNT` (в `.env` локально или в переменные окружения хостинга).
   - Файл содержит приватный ключ — храните как секрет, не коммитьте в git.

## ⚠️ ID базы Firestore (реальный, проверенный на этом проекте гочтя)

Firestore поддерживает несколько именованных баз в одном проекте. Раньше (до этой фичи) в каждом
проекте автоматически создавалась ровно одна специальная база с зарезервированным ID `(default)`,
и `admin.firestore()`/`getFirestore(app)` без аргументов всегда находили именно её. Сейчас Firebase
Console на шаге **Create database** просит явно ввести ID новой базы — и если ввести (или
согласиться с подсказкой) `default` **без скобок**, это будет отдельная именованная база, а не
специальная `(default)`. Клиент, который ищет `(default)`, её не найдёт и упадёт с ошибкой
`NOT_FOUND`.

Из-за этого `src/lib/db.js` **всегда** передаёт ID базы явно вторым аргументом в
`getFirestore(app, id)`, а не полагается на аргумент по умолчанию. ID берётся из
`FIREBASE_FIRESTORE_DATABASE_ID` (по умолчанию `default` — так называется база в этом проекте,
подтверждено прямой проверкой сервисного ключа: запись+чтение тестового документа прошли успешно
именно с этим ID). Если ваша база — классическая `(default)` (создавалась до появления выбора ID,
или вы явно ввели `(default)` со скобками) — переопределите переменную значением `(default)`.

Проверить, как называется ваша база: Firebase Console → Firestore Database → в шапке страницы
рядом с названием проекта показан ID текущей базы.

## Что бот создаёт в Firestore сам

Никаких миграций запускать не нужно — коллекции и документы создаются автоматически при первой
записи (`set(..., {merge: true})` создаёт документ, если его ещё нет):

| Путь | Что | Кто пишет |
|---|---|---|
| `bot_logs/<auto-id>` | Структурированные логи запросов/ответов | `src/lib/logger.js` (пакетно, batch до 50 записей) |
| `bot_state/main` | Тумблеры событий, ID основного чата, темы форума | `src/lib/stateStore.js`, при `/toggle_event`, `/set_main_chat`, `/set_topic` |
| `stats_daily/<YYYY-MM-DD>` | Счётчики статистики за текущие сутки (UTC) | `src/lib/stats.js`, атомарный инкремент на каждое событие |

## Бесплатный тариф (Spark) — на что обратить внимание

- **50 000 чтений / 20 000 записей / 20 000 удалений в день** — для тестового контура с редкими
  событиями VK этого с большим запасом достаточно. Каждое входящее событие VK/Telegram — это
  1 запись лога + 1-2 инкремента счётчика (batched, но Firestore считает каждый документ отдельно
  вне зависимости от батчинга).
- `/health` делает 1 чтение (`bot_logs.limit(1).get()`) на каждый вызов — если настроите внешний
  keep-alive/аптайм-мониторинг, не делайте его слишком частым (раз в минуту — не проблема, раз в
  секунду — будет заметно есть квоту).
- Квота сбрасывается ежедневно в полночь по тихоокеанскому времени (PT), а не UTC — так же, как
  день для `stats_daily` считается по UTC (это два независимых календаря, не путайте при отладке).

## Отличие статистики от прежней SQL-версии

Раньше (Supabase) `/stats` считал скользящее окно "последние 24 часа" через SQL-вьюхи. Сейчас —
атомарные счётчики за **текущие календарные сутки UTC** (`stats_daily/<дата>`), без истории по
дням и без скользящего окна. Компромисс сознательный — ради минимальных чтений/записи и простоты
(подробности и обоснование — в шапке `src/lib/stats.js`).
