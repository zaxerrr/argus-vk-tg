## Факты о free-тарифе (по документации)

| Параметр | Значение |
|---|---|
| Ресурсы | 0.1 CPU, 512 MB RAM, один инстанс, без масштабирования |
| Сон | через **15 минут без входящего трафика** (HTTP-запросы и сообщения по уже открытым WebSocket) |
| Пробуждение | входящий HTTP-запрос; занимает **около минуты** |
| Лимит часов | **750 free-часов в календарный месяц на весь workspace**; спящий сервис часы не тратит. Если часы кончились, все free-сервисы workspace приостанавливаются до начала следующего месяца |
| Трафик и сборки | расходуют включённые исходящий трафик и минуты сборки; при превышении — оплата или приостановка (без карты) |
| Файловая система | эфемерная: всё теряется при деплое, рестарте и засыпании. Persistent disk недоступен |
| Рестарты | «Render might restart a Free web service at any time» |
| Прочее | нет Shell/SSH; исходящие SMTP-порты 25/465/587 закрыты; порты 18012, 18013, 19099 зарезервированы |

## Деплой и рестарты

- **Zero-downtime деплой действует и для free.** Старый инстанс принимает трафик, пока
  поднимается новый. Когда новый стал healthy, трафик переключается на него, а **через 60 с**
  старому приходит `SIGTERM` (по умолчанию ещё до 30 с на завершение, потом `SIGKILL`; настройка
  `maxShutdownDelaySeconds`, 1–300).
- Следствие для long-polling: примерно 1–2 минуты после каждого деплоя **два процесса делают
  `getUpdates` одним токеном**, и Telegram отвечает одному из них `409 Conflict`. Это ожидаемо.
  `src/telegram.js` пишет об этом одну строку в минуту, а не стек на каждую попытку. Если 409
  держится дольше — тот же токен запущен где-то ещё.
- `server.js` по `SIGTERM` останавливает polling и дописывает очередь логов в Firestore.
- **Смена переменной окружения не применяется рестартом** — нужен деплой («restarting does not
  incorporate those changes»). После правки Environment нажимайте **Manual Deploy**.
- В `render.yaml` у переменных с `sync: false` значение спрашивается **только при первом
  создании Blueprint**. Новые переменные в существующем сервисе добавляйте руками в Environment.
- `autoDeploy` в Blueprint устарел, используется `autoDeployTrigger: commit` (исправлено
  2026-09-26).
- Лимиты времени: сборка 120 мин, запуск (`startCommand`) 15 мин.

## Health checks

- Render шлёт `GET healthCheckPath` (`/health`) **каждые несколько секунд**. Успех — ответ
  2xx/3xx за 5 с. После 15 с неудач трафик снимается с инстанса, после 60 с инстанс
  перезапускается.
- `/health` всегда отвечает 200: недоступный Firestore — не повод перезапускать бота.
- Раньше каждый `/health` читал документ из Firestore. При проверке раз в несколько секунд это
  тысячи чтений в сутки из бесплатных 50 000. Теперь результат пинга Firestore кэшируется на
  60 с — не больше 1 440 чтений в сутки (исправлено 2026-09-26).
- Не проверено: не дают ли health checks сервису заснуть. По факту наш сервис засыпает, значит,
  не дают.

## Порт и переменные

- Render задаёт `PORT` (по умолчанию `10000`); бот слушает `process.env.PORT`, запасной `3000`
  нужен только локально. Привязка должна быть на `0.0.0.0` — Express по умолчанию так и делает.
- Полезные переменные, которые Render выставляет сам: `RENDER=true`, `RENDER_EXTERNAL_URL`
  (`https://<имя>.onrender.com`), `RENDER_GIT_COMMIT`, `RENDER_SERVICE_ID`, `RENDER_INSTANCE_ID`,
  `NODE_ENV=production`.
- Входящие запросы идут через Cloudflare и балансировщик Render. Без `app.set('trust proxy', …)`
  `req.ip` — адрес прокси, **один на всех клиентов**. Поэтому rate limiter по IP за Render
  фактически общий. В боте он теперь ограничивает только запросы с неверным секретом, чтобы флуд
  не отнимал лимит у настоящих событий VK (подробности — `docs/VK_API.md`, «Ответ, повторы и
  приостановка»).

## Версия Node.js

- Порядок выбора: `NODE_VERSION` в Environment → `.node-version` → `.nvmrc` → `engines` в
  `package.json`. Для новых сервисов по умолчанию стоит 24.x.
- **Диапазон без верхней границы (`>=18`) всегда разрешается в latest Node** и сам переезжает на
  новые мажорные версии. Раньше в `package.json` было `>=18`. Теперь `"22.x"` — LTS, на ней
  проходят тесты (исправлено 2026-09-26). CI гоняет 22.x и 24.x; Node 18 и 20 уже вне поддержки.

## Что сон значит для бота

| Ситуация | Что происходит | Как смягчено |
|---|---|---|
| Команда боту, пока сервис спит | Long-polling — исходящий трафик, он не будит сервис и не мешает ему заснуть. Команда ждёт. Telegram хранит апдейты до 24 ч, и ответ придёт, когда сервис разбудит что-то другое (событие VK, пинг) | Keep-alive пинг (ниже) или переход Telegram на webhook (в планах) |
| Событие VK, пока сервис спит | Запрос будит сервис (~1 мин). VK, скорее всего, не дожидается `ok` и повторяет через 10 с, 3 мин… (`X-Retry-Counter` в логе) | Дедуп по `event_id` + Firestore `dedup_seen`, ключ захватывается до `await` |
| Несколько событий VK во время пробуждения | Несколько ошибок подряд. По документации VK это может **временно приостановить** отправку на сервер | Keep-alive пинг; если события пропадают часами — проверить вкладку «Запросы» в настройках Callback API |
| Рестарт/сон | Память процесса обнуляется | Тумблеры, темы и основной чат — в Firestore `bot_state/main`; дедуп — в `dedup_seen` |
| `STATS_DIGEST_HOURS` | Таймер `setInterval` живёт в памяти: сон и рестарт его сбрасывают. При интервале больше времени бодрствования дайджест может не прийти никогда | Пользоваться `/stats` по запросу; для надёжного расписания нужен внешний планировщик |
| 409 после деплоя | Два инстанса ~60–90 с | Ожидаемо, см. «Деплой и рестарты» |

## Keep-alive: держать сервис бодрствующим

Внешний пинг `GET https://<сервис>.onrender.com/health` каждые **10–14 минут** (UptimeRobot,
cron-job.org и т. п.):

- **Часы:** бодрствование 24/7 — 720 ч в 30-дневном месяце и 744 ч в 31-дневном. Это
  укладывается в 750 ч, **только если это единственный free-сервис в workspace**. Если есть
  другие free-сервисы, часы кончатся, и Render приостановит **все** free-сервисы до конца месяца.
- **Firestore:** с кэшем пинга `/health` не больше 1 чтения в минуту — квоту не съест.
- Не пинговать `/robots.txt`. По сторонним наблюдениям
  ([odown.com](https://odown.com/blog/how-to-keep-a-render-free-service-from-sleeping/)) пока
  сервис спит, Render отвечает на него сам, и сервис не просыпается.

Альтернативы без пинга:
- план **Starter** — не спит, нет лимита часов;
- **Telegram в режиме webhook** вместо long-polling: апдейты Telegram станут входящими
  HTTP-запросами — будят сервис и снимают 409 при деплое. Это изменение кода
  (`bot.setWebHook(RENDER_EXTERNAL_URL + '/telegram/<секрет>')` + маршрут с `bot.processUpdate`).
  Его надо проверить на реальном токене — см. раздел про `node-telegram-bot-api` в `CLAUDE.md`.
